# Candidate resident snapshot fixture

This fixture composes the fixed
[installation root](../../../docs/LINUX-CUSTODY-ROOT.md), version 2
[record codec](../../../docs/LINUX-CREATION-ADMISSION.md#candidate-codec-boundary)
and an encrypted package selected by the same credential identifier.
It tests a read-only candidate, not a trusted attended producer or operational
creation admission. Normal Linux custody remains unavailable.

The candidate and shared package-format source are compiled in the disposable
helper. The product manifest and lock do not gain the experimental OpenSSH
parser dependency. The helper uses `ssh-key` 0.6.7 with `std` and without
`encryption`; parsing exposes the cipher, KDF and public header but does not
decrypt, unlock or sign. The writer retains encryption for its separate role.

## Data and authority

The encrypted key and manifest are public test data generated by the original
disposable writer using a public fixture password. No real credential, unlock
secret, project state or installation is imported. A retained baseline captures
the writer's exact exit codes and stdout/stderr for a valid package and malformed
variants. The refactored writer must reproduce those outputs byte for byte on
the same retained objects. Both writer and reader use one byte-validation source;
filesystem checks, revalidation and publication remain their separate concerns.

Administrative setup uses the real candidate provisioner to create independent
real and decoy bindings inside new volumes. After the writer has exited, the
setup observer populates synthetic public package and record slots. It temporarily
owns the private leaf containers while preparing fixtures, then hands every
resident object and the containers back to the target UID/GID. This is fixture
construction, not the operational producer or a source of creation evidence.

The reader receives only a case and an observer channel. Its candidate API takes
the canonical credential ID; it opens the literal namespace root internally.
No package path, root descriptor, endpoint key or expected installation ID is
supplied to it. The observer independently compares the selected installation
with setup's generated binding, and the credential with the resident slot.

## Required observations

| Case | Required observation |
|---|---|
| `resident-valid` | Root, record and resident encrypted package agree and the held snapshot validates |
| `resident-unrelated` | Publishing another credential while the snapshot is held does not invalidate it |
| `missing-record` | No record slot refuses without repair or package-based fallback |
| `missing-package` | A record without its resident package refuses |
| `experimental-record` | Experimental version 1 metadata does not become a version 2 expectation |
| `installation-mismatch` | Record and independently selected binding disagree |
| `credential-mismatch` | The record cannot select another credential from its resident slot |
| `manifest-mismatch` | The record's device identity disagrees with the package manifest |
| `ciphertext-mismatch` | Record digest and exact encrypted bytes disagree |
| `record-in-place` | Different canonical record bytes on the same inode invalidate the held snapshot |
| `record-replacement` | Identical bytes on another record inode invalidate it |
| `package-replacement` | An identical package in another directory object invalidates it |
| `key-in-place` | Different key bytes on the same inode invalidate it |
| `key-replacement` | Identical key bytes on another inode invalidate it |
| `manifest-replacement` | Identical manifest bytes on another inode invalidate it |
| `mount-record-slot` | An additional mount at the record directory refuses with EXDEV |
| `mount-record-leaf` | An additional mount at the record file refuses with EXDEV |
| `mount-package-slot` | An additional mount at the package directory refuses with EXDEV |
| `mount-key-leaf` | An additional mount at the key file refuses with EXDEV |
| `mount-manifest-leaf` | An additional mount at the manifest file refuses with EXDEV |
| `symlink-record` | A controlled record symlink refuses with ELOOP |
| `hardlink-key` | A key with a second hard link outside its slot refuses |
| `acl-record` | An actual extended access ACL refuses even when mode remains 0600 |

Every mutation begins after the reader has captured and validated the target.
It retains that same candidate while an independently owned mutator completes
one case-bound token request. The controller checks the mutator's identity,
exit and exact before/after object/digest properties before acknowledging the
request. The reader then validates the retained snapshot without reopening an
installation or refreshing the selected identity. Request/ACK files are bounded
fixture coordination, not an operational authority protocol.

Mount cases require actual kernel mount evidence, read-only configuration and
continuity of device and inode with setup. A distinct mount ID over the same
underlying object must still be rejected. A declaration of NO_XDEV, an unsupported
Docker mount or an arbitrary constructor failure earns no successful observation.
No probe process receives SYS_ADMIN or performs a mount syscall.

## Resource and process boundaries

| Role | UID/GID and capabilities | CPU | RAM | PIDs | Temporary storage |
|---|---|---:|---:|---:|---:|
| Setup, alone | 0:0; CHOWN and DAC_READ_SEARCH only | 1 | 512 MiB | 128 | 128 MiB |
| Reader | 65534:65534; none | 0.75 | 320 MiB | 96 | 96 MiB |
| Mutator, only on request | 65534:65534; none | 0.25 | 128 MiB | 16 | 16 MiB |

Setup exits before the other roles start. Reader and mutator together stay within
1 CPU, 448 MiB RAM, 112 PIDs and 112 MiB temporary storage. Each container has no
network, NNP, a read-only image root and no additional swap. Source, fixture and
helper are read-only. The reader's real and decoy volumes are read-only; only
the mutator receives its case's real volume read-write. The setup procedure and
mutator cannot alter the installation in use.

The observer retains pidfds and checks process, parent/start and executable
identity, real/effective credentials, NNP and every thread's capabilities.
The Rust reader runs four pressure threads. Final success requires its actual
observed exit code 0 and resource closure; a timeout or killed process does not
count as success. Cases run under separate RustWork leases so other projects
may run between them. Selected RDP errors stop the active batch.

## Scope and reproduction

All creation-origin, creation-admission, root-bootstrap, provisioning, custody,
endpoint-authority, recovery, server/MCP and lock acknowledgements remain false.
A structurally consistent public snapshot does not demonstrate that the trusted
attended producer created it. That producer, the complete durable transaction,
native initial validation and operational reader adoption need their own gates.
No organization membership, permission, physical-host identity, anti-rollback
or power-loss guarantee follows from this fixture.

Build and verify the isolated helper, then run each case separately through the
shared coordinator with `--family rust`:

```text
python run_resident_probe.py --case CASE --image LOCAL_UBUNTU_IMAGE --launcher-build-volume VERIFIED_HELPER_VOLUME --fixture-dir ABSOLUTE_PUBLIC_FIXTURE_DIRECTORY --reports-dir NEW_ABSOLUTE_REPORT_DIRECTORY
```

The controller removes its own stopped containers and temporary real/decoy
volumes. Report volumes, the public fixture and selected build volumes are
deliberately retained by identity as evidence; they are not claimed as deleted.
An incomplete attempt remains incomplete even if cleanup succeeds.
