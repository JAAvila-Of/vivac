# Linux terminal-input experiment

This development-only experiment tests password acquisition before the isolated
OpenSSH writer generates entropy or opens its destination. It does not enable a
Linux device-key backend. All input and SSH credentials are synthetic. Run only
in a disposable Linux container with no real home, login keys, forwarded agent
or provenance tree mounted.

## Input contract

The writer's optional `--terminal` mode opens `/dev/tty` directly and requires
the foreground process group. Caller stdin is not a fallback. It uses Linux's
canonical terminal discipline, a fixed read buffer and two explicitly terminated
lines. The accepted password has 16 through 512 UTF-8 bytes, without NUL, and
must match its confirmation exactly. CR is treated as the terminal's Enter
character; it is not password data. Empty reads and incomplete lines, including
Ctrl-D after a nonempty prefix, refuse. The kernel's canonical line limit is
larger than the accepted password limit, so kernel truncation cannot turn an
oversized line into an accepted password.

Echo changes must be read back successfully. The managed signals are HUP, INT,
QUIT, TERM, TSTP, TTIN and TTOU. They are blocked while terminal state is changed
and observed synchronously through
`signalfd` and `poll`. No process-global signal handler edits terminal state.
Cleanup flushes pending input, restores the original attributes, checks them
and restores the previous signal mask. A failed cleanup refuses creation. The
last cancellation check occurs with the mask still blocked after terminal
restoration; events after that boundary are not a transactional cancellation
guarantee for later encryption or file publication. The
experimental pair of reads has a 15-second deadline; this is not an adopted
product interaction policy.

The code is confined to a single-threaded helper. It does not establish safe
integration into a multithreaded host. Other signals and abnormal process faults
are not restoration guarantees. SIGKILL and SIGSTOP cannot be caught by this
mechanism. A destroyed or failed terminal may not permit
restoration at all; refusal is not a claim that the terminal was repaired.
Reading a password cannot establish later signing-session shutdown or protect
the library's internal copies of plaintext.

## Why existing readers were insufficient

The reviewed `rpassword` reader can grow before a caller checks length, and
returns transformed input without distinguishing every EOF case. The reviewed
`readpassphrase` API bounds writes but returns the same successful C-string
shape after EOF or Enter and silently discards excess bytes. `passterm` provides
strict UTF-8 and a limited read, but its Unix path lacks cleanup on default
termination signals. A validation wrapper applied after these operations does
not recover the missing evidence.

This experiment uses the operating system's terminal and signal interfaces,
not a new password or cryptographic protocol. The only direct binding added to
the isolated writer is the `libc` version already present in its locked graph.
The product manifest and dependency lock are unaffected.

## Verification boundary

The fixture must check terminal attributes independently while prompts are
visible and after the child exits, including refusal paths. Its positive cases
parse the resulting encrypted file. Its negative cases require an absent
destination; timeout in the fixture is a test failure. It must not retain
terminal contents or key fixtures in its metadata report.

PTY observations alone do not establish SSH behavior. A separate loopback SSH
server and pinned synthetic host/client keys exercise a real remote terminal,
EOF and cancellation, transport disconnection and a fresh connection. When
disconnection destroys the terminal, restoration is not observable; the test
can establish refusal and process exit, not restored attributes on that device.
No SSH service on the host or remote user machine is involved.

The terminal-input result cannot approve encrypted package publication,
identity binding, rollback handling, a persistent OS protection backend or the
unlocked agent's lifecycle. Those remain independent admission conditions.

## Reproduction

Build and test the isolated writer as described in [OPENSSH.md](OPENSSH.md).
`Dockerfile.terminal` supplies the disposable SSH server image. It changes only
that image's synthetic root-account password field to an invalid hash, disables
password authentication in the fixture configuration and removes host keys
generated by package installation. The fixture generates its own temporary
transport keys and pins the host public key; it never uses a login agent or
accepts an unknown host key.

Run the image with a read-only root, `--network none`, a private writable `/tmp`
with mode 0700, and only SETUID, SETGID, SYS_CHROOT, KILL and AUDIT_WRITE
capabilities. The isolated server needs to manage its privilege-separation
children and write native audit events. The fixture also requires that the
network namespace expose only loopback. Mount this review directory and the
Linux writer binary read-only,
and mount a separate metadata-report directory writable. Do not mount a real
home or project state. AUDIT_WRITE can emit events to the Docker host kernel's
audit log; network isolation does not isolate that log. Use a disposable Linux
host or runner when the audit log must also be disposable.

Inside that container, with the disposable declaration:

```text
python3 /probe/terminal_probe.py --writer /writer/debug/ssh-writer-graph-audit --report /reports/new-terminal-observations.json
```

The report destination must be new. The runtime report records executable and
script provenance and individual case outcomes, not terminal transcripts or
passwords. The workflow runs this fixture only with the explicit
`openssh_profile_review` dispatch input. A configured CI step is not evidence
that CI has passed. On the shared Windows account, wrap the entire Docker
runtime suite with RustWork and `--family rust` because it executes Rust.

## Observed result

The local disposable Ubuntu 24.04 run used OpenSSH 9.6p1-3ubuntu13.20 and a
writer built and unit-tested on Rust 1.95. The complete PTY and loopback-SSH
matrix passed with `custody_accredited: false`.

| Boundary | Observed result |
|---|---|
| Accepted terminal input | Normal, minimum/maximum byte lengths and UTF-8 fixtures produced encrypted GCM/bcrypt files, with echo off at each prompt and exact terminal restoration. |
| Invalid terminal input | Empty, short, oversized, kernel-limit-sized, NUL, invalid UTF-8, mismatched and incomplete EOF input refused without a destination. |
| Cancellation | Managed interrupt, hangup, termination, quit and suspend cases refused and restored the live terminal. Inherited ignored HUP/TERM dispositions also delivered cancellation through the blocked signal descriptor. |
| No input or no controlling TTY | The explicit reader deadline and the separate-session no-TTY case refused without a file. A fixture timeout was never counted as success. |
| Real SSH terminal | Successful creation, partial EOF and TERM cases independently verified the remote echo transition, foreground group and the writer's own restoration before wrapper cleanup. |
| SSH disconnection and reconnect | Closing the SSH client caused the remote reader to exit without a destination. Restoration on the destroyed terminal was not observable. A fresh SSH connection created a new encrypted file and restored its terminal. |

These are observations of this fixture, not all Linux systems or terminal
drivers. The subsequent [package experiment](PACKAGE.md) rebuilt the writer on
Linux with Rust 1.89 and reran this complete terminal/SSH fixture successfully.
No remote CI run, production backend, signing-agent
supervisor or crash guarantee follows from this result.
